# 灰度放量演练台（Flask + SQLite + Docker Compose）

值班员灰度演练页：每轮按当前新版流量比例把 10 笔样例请求分给新/旧版，网页逐笔回填
成败；30 秒窗口内收齐且新版失败率不高于旧版，才可确认放量 +10 个百分点，到 100% 停止；
超时或超标留在原档、可重开采样。

## 一、启动方式

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

- 数据存于命名卷 `canary-data` 内的 SQLite 库 `/data/canary.db`（WAL 模式），容器重建不丢数据。
- 容器以 gunicorn 2 worker × 4 线程运行，专门用于验证并发场景。
- 窗口时长由环境变量 `CANARY_WINDOW_SECONDS` 控制，默认 30；演练晚到场景时可临时调小。
- 本地无 Docker 时的等价启动：`pip install -r requirements.txt && gunicorn --bind 0.0.0.0:8000 wsgi:app`
  （需设置 `CANARY_DB` 为可写路径）。

## 二、实现说明

### 数据模型（`app/db.py`）

| 表 | 作用 |
|---|---|
| `meta` | 单行：当前档位 `rollout_pct`（10 起）、`finished`（到 100% 置位） |
| `rounds` | 每轮采样：序号、发出档位、新/旧笔数、状态机 `open/confirmed/rejected/expired`、发出/截止/关闭时间、判定依据 |
| `requests` | 每轮 10 笔不可变样例，带轮次与版本（new/old） |
| `receipts` | 回执；`request_id UNIQUE` 数据库级保证每笔只留首个回执；`late=1` 表示轮次关闭后晚到，仅留档 |

关键约束与事务：

- **回执归轮次/版本**：回执插入时从不可变的 `requests` 行复制 `round_id、version`，
  换轮后的旧回执物理上不可能计入新轮判定。
- **首个回执为准**：`receipts.request_id` 唯一约束兜底，并发回填只有一笔成功，其余 409。
- **并发确认只推进一次**：确认接口使用 `BEGIN IMMEDIATE` 抢写锁 + 轮次状态机
  （仅 `open` 可确认），10 个并发请求只有 1 个能改 `meta`；旧轮次的重复确认一律 409。
- SQLite 开启 WAL + `busy_timeout=10s`，配合 gunicorn 多 worker 短事务，读写不互斥阻塞。

### 业务规则（`app/app.py`）

1. **拆样例**：`new_n = floor(当前比例 × 10)`，其余给旧版。10%→1 新 9 旧 …… 90%→9 新 1 旧。
2. **30 秒窗口**：开轮时写入 `deadline_at`；任何请求进来先 `sweep_expired()` 把过点仍
   `open` 的轮次自动置 `expired`（无需后台线程）。
3. **晚到回执**：轮次非 `open` 时收到的回执标 `late=1`，页面与统计均排除，只留档展示。
4. **确认条件**（全部满足才 +10%）：
   - 当前时间未过截止；
   - 窗口内有效回执收齐 10 笔；
   - 新版失败率 ≤ 旧版失败率。
   - 不满足分别落 `expired` / `rejected`，`meta` 档位不变，可重新开轮。
5. **停止**：推进到 100% 后 `finished=1`，禁止再开轮。
6. 每次确认都把人可读的判定依据（收齐数、两版失败率、档位变化）写入 `rounds.decision_note`，
   页面历史表可查。

### 页面（`app/templates/index.html` + `static/`）

- 顶部显示当前档位、服务器时间；
- 当前轮分「新版 / 旧版」两栏展示回收数、待回数、成败数、失败率与晚到数；
- 逐笔表格提供「回填成功 / 回填失败」按钮，已回填笔显示首个回执已锁定；
- 「放量依据」清单实时显示收齐进度、失败率对比、确认后档位与超时/超标处置；
- 历史轮次表展示每轮档位、拆分、状态与判定记录；前端每秒轮询 `/api/state` 自动刷新。

### HTTP 接口

| 方法路径 | 说明 |
|---|---|
| `GET /api/state` | 全量状态（含自动超时扫描后的结果） |
| `POST /api/rounds/open` | 开一轮采样（有 open 轮或已 finished 时 409） |
| `POST /api/requests/<id>/receipt` | 回填 `{"success": true/false}`；重复 409；晚到返回 `late:true` |
| `POST /api/rounds/<id>/confirm` | 确认放量；未收齐/超时/超标/重复确认均 409 并附原因 |
| `POST /api/rounds/<id>/expire` | 演练辅助：立即把当前轮置超时（生产可移除） |

## 三、实测结果

测试均针对**真实 gunicorn 双 worker 进程**（非单进程模拟），SQLite 落真实文件。

### 1. 端到端套件 `tests/e2e_test.py`（窗口加速为 3 秒）

```
结果：38 通过 / 0 失败
```

覆盖：

- 10% 档拆 1 新 9 旧、全成功收齐 → 放量 10%→20%；
- 二次确认被 409 拒绝，档位不变（旧确认不能再次推进）；
- 同一笔顺序重复回填、8 线程并发回填，均只有首个回执生效；
- 窗口超时自动 `expired`、档位不动；**晚到失败回执标 late 且失败统计保持 0**；
- 重开轮的回执从零开始，旧轮回执不影响新轮；
- **10 线程并发确认同一轮：仅 1 次成功，档位只推进一格（40%→50%）**；
- 新版失败率 40% vs 旧版 0% → `rejected` 留 50%；连续超标均留档；新版 0% ≤ 旧版 20% 时通过；
- 连续放量 60%→70%→…→100%，各档拆分正确，100% 后 `finished` 且禁止再开轮。


## 四、未完成项 / 环境限制

1. **本机未安装 Docker/Podman，未实际执行 `docker compose build/up`**；Dockerfile 与
   compose 配置按标准 python:3.11-slim + gunicorn 编写并通过 YAML 校验，全部功能已在
   同版本 gunicorn 27.0.1 / Flask 3.1.3 / Python 3.11 真实进程下实测，建议有 Docker
   的环境再跑一次 `docker compose up --build` 做最终确认。
2. 无登录鉴权与操作审计（演练工具定位；如需多人值班可再加登录与操作日志表）。
3. 样例请求为演练用的模拟数据（编号 `R轮次-序号-版本`），未对接真实业务流量；
   接入时把开轮逻辑替换为真实请求下发即可，回执回填接口可直接复用。
4. 超时判定采用"请求驱动"扫描（每次 API 调用先 sweep），无后台定时器；页面每秒轮询
   可保证及时触发，若未来无人访问又需要精确超时回调，可再加一个调度线程。
5. `POST /api/rounds/<id>/expire` 是为演练加速准备的辅助接口，生产部署建议删除或加权限。
